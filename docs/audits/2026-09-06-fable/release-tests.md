## P1 — Выключатель аналитики не работает в трёх задокументированных случаях

**Статус:** подтверждено чтением кода (без запуска). **Внесено:** механизм импортирован в диапазоне (`e3d900b`, 3 сентября) из более ранней Claude-ветки `7c6cb92` (22 августа) без изменений в этой части — дефект существовал до Codex-эры и не является её регрессией. **Совпадает** с находкой F2 предыдущего раунда; я перепроверил каждую цепочку по коду независимо.

Три публичных документа — `docs/analytics.md:10-11`, `PRIVACY.md:28-29`, обе privacy-страницы лендинга (`landing/privacy/index.html:34`, `landing/ru/privacy/index.html:34`) — подают три способа выключения как равноценные: окно setup, Settings → Setup, `amanu analytics off`. Фактически:

**(a) `amanu analytics off` не действует на работающее приложение до его перезапуска.** `AnalyticsCommand.swift:27` пишет config и постит `Config.didChange` — но это внутрипроцессный `NotificationCenter` (`Config.swift:554`); сink приложения слушает только его (`AnalyticsSink.swift:119-126`). Файлового наблюдателя нет нигде (grep по `Sources/` на `makeFileSystemObjectSource`/`NSFilePresenter` пуст), `send()`/`record()` переключатель не перечитывают (`AnalyticsSink.swift:147-152, 217-229`). Amanu — резидентное меню-бар-приложение и login item; «до перезапуска» — это дни и недели, в течение которых события с постоянным UUID продолжают уходить каждые 30 секунд после явного отказа.

**(b) Включение после запуска в выключенном состоянии тоже не работает.** `start()` ставит `started = true`, затем `guard enabled else { return }` — **до** `watchTheSwitch()` (`AnalyticsSink.swift:99-112`). Запустились с `analytics: false`, включили тумблер в Settings — уведомление постится, но наблюдателя нет, а повторный `start()` отсекается `guard !started`. Тумблер «включить» действует только со следующего запуска — ровно то, что комментарий в этом же файле (`AnalyticsSink.swift:117-118`) называет недопустимым.

**(c) Обещание «Turning analytics off deletes that file along with everything in it» (`docs/analytics.md:160-161`) выполняется только на одном пути.** Удаление `analytics-pending.json` происходит лишь в `reread()` работающего включённого синка (`AnalyticsSink.swift:135-142`). При выключении через CLI файл не удаляется никогда (в CLI синк при `off` вообще не стартует — `AnalyticsCommand.swift:37`); при следующем запуске приложения с выключенной аналитикой `start()` выходит до любой очистки. Данные остаются локально (не утекают), но обещанное удаление не происходит. Мелкая гонка там же: завершение уже летящего `send()` после `reread()` пересоздаёт файл пустым (`savePending()` в замыкании `AnalyticsSink.swift:237-244` не проверяет `enabled`).

**Влияние.** Для продукта, публично строящегося на проверяемости приватностных утверждений («the complete list… is what lets that sentence stand without hedging»), это самое уязвимое место запуска: сценарий «выполнил `amanu analytics off` — смотрю в Little Snitch — приложение продолжает POST-ить на `stats.amanu.me`» проверяется любым дотошным пользователем за минуту.

**Регрессионные тесты.** (1) синк, стартовавший при off, после `switchIsOn→true` + `didChange` буферизует событие (сегодня падает); (2) синк, стартовавший при on, после внешнего `switchIsOn→false` без уведомления не передаёт ничего при следующем тике (сегодня падает); (3) путь `off` удаляет pending-файл. Первые два фактически уже написаны предыдущим аудитором в нетрекаемом `AnalyticsConsentTests.swift`.

**Направление фикса.** Вынести `watchTheSwitch()` из-под `guard enabled` (лечит b); перечитывать `switchIsOn()` в начале `send()` — одно чтение файла раз в 30 секунд (лечит a для отправки); удалять pending при `off` в `AnalyticsCommand`/при старте с выключенным переключателем (лечит c). Для мгновенного эффекта CLI→приложение проектно-чистый вариант — распределённое уведомление рядом с локальным в `Config.update`: distributed notifications — санкционированный IPC этого проекта (CLAUDE.md, «Two standing decisions»).

## P2 — Русская витрина: грамматическая ошибка в главном тексте, закреплённая тестом

**Статус:** подтверждено. **Внесено:** в диапазоне — `a933695` «Revise the Russian summary copy» (2 сентября).

`landing/ru/index.html:96`: «Я считаю, что **модели должны работают** по-полной…» — «должны работают» грамматически невозможно (модальный глагол + личная форма); правильно «должны работать». Диф показывает, что предыдущая версия была грамотной («…а модели пусть работают по-полной») и сломалась именно при переформулировке; тот же коммит добавил в `landing/tests/check.py:246-250` проверку, требующую **дословно этот** текст (и заголовок проверки повторяет ошибку). То есть исправление страницы без исправления теста уронит CI и стадию 1 релиза. Рядом второе, менее кричащее: `landing/ru/index.html:93` — «В других подобных программах**,** создатели экономят токены» — запятая между обстоятельством и подлежащим (внесено `8006159`, тоже в диапазоне).

**Влияние.** `/ru/` — версия для основной аудитории (nginx целенаправленно редиректит русские браузеры, `deploy/nginx/amanu.conf:59-64`); ошибка стоит в одном из четырёх смысловых блоков продукта. Для запуска, где продукт конкурирует качеством текста выжимок, безграмотная фраза ровно в блоке «Качественные выжимки» — антиреклама.

**Фикс.** Поправить оба предложения и синхронно — строку и заголовок проверки в `check.py`. Если формулировка была авторской диктовкой — подтвердить у автора, но «должны работают» не может быть намеренным.

## P3 — Серверная аналитика: обещание ретенции держится на ненаблюдаемом таймере (частично гипотезы)

6. **Отказ ретенции никому не виден.** «Kept for a year, then deleted» (`docs/analytics.md:19`) исполняет один systemd-oneshot без `OnFailure=` (`amanu-stats-retention.{service,timer}`); сервис к тому же хардкодит `-U umami -d umami` мимо `.env` (`retention.service:9` против `env.example`; `weekly_digest.py:120-124` читает `.env` правильно). Имена таблиц `revenue`/`heatmap_event`/`session_replay` против реальной схемы Umami 3.3.0 из репозитория не проверяемы — при любом несовпадении `ON_ERROR_STOP` тихо валит всю транзакцию каждую ночь. Smoke-тест (`retention-smoke-test.sql`) создаёт собственные таблицы, то есть проверяет логику, а не схему, и не покрывает единственную ветку, ради которой написаны `NOT EXISTS` («старая сессия со свежим ребёнком» — переживает год вместе с coarse-геоданными; для Umami с помесячной ротацией соли сценарий почти теоретический, но smoke-тесту третья фикстура нужна). **Требует одного ручного прогона на сервере** + `OnFailure=` или строка «возраст самой старой записи» в еженедельном дайджесте.
7. **`PRIVATE_MODE: "1"` в `docker-compose.yml:14`** — я не смог подтвердить, что Umami 3.3.0 знает такую переменную; если нет, она инертна. Гипотеза, требующая проверки на сервере; на приватностные обещания документации не влияет (там про геолокацию сказано честно).
8. **Ошибки `weekly_digest.py` глотаются**: `subprocess.run(..., capture_output=True, check=True)` (`weekly_digest.py:125-127`) — в journald попадёт трейсбек без stderr psql. Однострочный `except CalledProcessError: print(e.stderr)`.
9. **Словарь**: `reports.sql:27` фильтрует `trigger neq "cli"` — значения `cli` не существует (реальные: `manual`, `mic-activity`, `calendar`, `RecordingSession.swift:43-47`); фильтр безвреден, но документирует несуществующее измерение.
